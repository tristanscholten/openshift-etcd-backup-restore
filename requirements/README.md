# Requirements traceability

Status: as-built v0.2 candidate. Source: task contract and OCP 4.20 implementation contract. This document records implemented behavior, not production validation.

| ID | Requirement | Evidence | Verification |
|---|---|---|---|
| REQ-BACKUP-01 | After explicit installation confirmation, the role shall install a timer on only the nominated backup source at 00:00, 06:00, 12:00, and 18:00 UTC, with exact OCP 4.20.z and cluster identity loaded only from a root-only host EnvironmentFile. | role defaults/tasks/templates | syntax and rendered-template tests |
| REQ-BACKUP-02 | The runner shall promote only a vendor-successful snapshot/static-resource pair with metadata and SHA-256 values, validate every complete candidate before retention, then retain at most three valid managed sets. | runner script | fixture runner tests |
| REQ-BACKUP-03 | For a newly promoted HA set, the runner shall use only a root-only authorized healthy-cluster kubeconfig to capture allow-listed Node/Machine/CPMS identity fields, bind its 0600 inventory and digest to the exact non-circular snapshot/static-resource pair, and fail promotion without pruning existing valid sets if capture fails. SNO needs no HA inventory. | runner, capture helper, root-only EnvironmentFile/config | simulated runner capture-failure retention test; validator schema and hash tests |
| REQ-DISCOVERY-01 | Read-only discovery shall invoke the validator on each managed source candidate and print metadata only for valid complete sets. | list-backups playbook | `tests/run_actual_list_fixture.py` executes the actual playbook against valid and hash-corrupt disposable candidates; the corrupt set and archive contents are absent from emitted discovery output |
| REQ-RESTORE-01 | Before any HA mutation, the restore playbook shall require a selected validated schema-2 set with its bound 0600 inventory; it shall prove the exact three reached hostnames, recovery host, and reproduced stable SSH identities match that capture. Machine mapping is derived only from that record and no `ha_machine_map` override exists. It shall also require explicit set/cluster/confirmation, exact installed 4.20.z, topology, source/recovery hosts, kubeconfig, and absolute executable `oc`. | restore playbook; validator | simulated actual-playbook fixtures reject incompatible versions and missing or mismatched offline evidence before timer/fence/restore mutation |
| REQ-RESTORE-02 | The restore playbook shall validate and fetch the selected set exactly once from the nominated source, re-hash it on recovery, fence all HA peers before one vendor restore, defer `oc` until API recovery, and execute post-API health/stability before a fresh backup/timer enablement. | restore playbook; source evidence | `tests/run_actual_restore_fixture.py` executes actual HA and SNO playbooks against disposable local simulated hosts and asserts source validation, fence, vendor, post-API, fresh-backup, and timer traces |
| REQ-RESTORE-03 | After API recovery, HA shall read-only reconcile captured Machine UID/NodeRef/providerID and Node UID/providerID (and CPMS mode) before deletion and freshly reconcile each remaining peer before its deletion. It shall DELETE through the authenticated local `oc proxy` API path with the exact Kubernetes `v1/DeleteOptions.preconditions.uid` for the just-reconciled Machine UID; it shall fail closed on proxy/API/409 conflict. It shall wait/checkpoint each peer, and stop before the second delete on failure. | reconciliation and UID-delete helpers; restore-ha-peer task | simulated actual-playbook ordering/body trace and name-reuse 409 fixture; not OCP DR-lab proof |
| REQ-RESTORE-04 | Before any timer pause, copy, fence, or restore, HA apply shall validate that the owner-supplied controller kubeconfig is an existing readable regular file; all hosts shall pass version, vendor/runtime/static-pod, disk, certificate-age, and protected-path gates. | restore playbook pre_tasks | executable missing-kubeconfig fixture and syntax/lint checks |
| REQ-RESTORE-05 | The workflow shall mark `VERIFIED` only after post-API operator/stability gates, a successful fresh source backup, and re-enabling the source timer. | restore playbook terminal tasks | syntax/lint and simulated trace coverage; OCP DR behavior remains unvalidated |
| REQ-RESTORE-06 | Before a HA Machine delete, the workflow shall read-only prove exactly the captured three control-plane Machine/Node identities (including recovery), current phase-appropriate operator health, and CPMS ownership/API when enabled. Each delete shall use an authenticated API UID precondition; the next delete is forbidden until one unambiguous healthy replacement is CPMS-controller-owned, checkpointed, and the fresh expected topology is reconciled. Backup capture and the installed validator shall reject duplicate hostname, Node, provider, and Machine identities across all three records. | capture helper; installed validator; reconciliation and UID-delete helpers; `restore_ha_peer` role | `run_actual_restore_fixture.py` recovery-mismatch/extra-master, unhealthy-operator, replacement-absent/replacement-unowned, name-reuse-conflict, and duplicate-inventory cases; matrix below |

## HA safety regression evidence

| Fixture | Source invariant | Base `4582908` outcome | Current outcome |
|---|---|---|---|
| `recovery-mismatch`, `extra-master` | exact three captured identities, no unrelated master | regression assertion fails (exit 1) | rejects before delete; durable `POST_API_MAP_RECONCILIATION_FAILED` |
| `unhealthy-operator` | read-only phase-appropriate health before delete | regression assertion fails (exit 1) | rejects before delete; durable `POST_API_MAP_RECONCILIATION_FAILED` |
| `replacement-absent` | no second delete until replacement proof | existing base protective stop (exit 0) | rejects after first delete with `HA_MACHINE_RECOVERY_INCOMPLETE`; no second delete |
| `duplicate-inventory` | duplicate identities/schema are refused before timer/fence | regression assertion fails (exit 1) | validator rejects before timer/fence |
| REQ-TEST-01 | A disposable local Podman etcd fixture shall snapshot, restore, and read back a marker key. | `tests/test_disposable_etcd_podman.sh` | executable local mechanics test; explicitly not OpenShift DR proof |
| REQ-UNINSTALL-01 | Uninstall shall require explicit confirmation, do nothing in check mode, remove only managed schedule/helpers from the nominated source, and never remove retained backup sets. | uninstall playbook | syntax and source guard tests |
| REQ-SAFETY-01 | The repository shall document its OCP 4.20-only and non-production-validation boundary. | docs | documentation inspection |
| REQ-CRONJOB-01 | The repository shall provide a self-contained `batch/v1` CronJob manifest that runs at `0 */6 * * *` UTC on one explicitly selected control-plane hostname, forbids overlap, uses bounded retry/runtime/history, and invokes the installed host vendor `cluster-backup.sh` through privileged `/host` chroot access without mounting an API token or granting cluster-admin. | `manifests/etcd-backup-cronjob.yaml` | YAML fixture structure assertions and `oc apply --dry-run=client` |
| REQ-CRONJOB-02 | After a successful vendor invocation creates exactly one new complete snapshot/static-resource pair in `/home/core/etcd-backups`, the CronJob shall mark that pair and retain the newest three marked complete pairs; it shall not prune if vendor invocation fails or is partial, and it shall not delete unmarked files. | embedded CronJob shell | disposable stub-vendor fixture executes the exact extracted shell for success, rotation, partial failure, and unrelated-file preservation |
| REQ-RESTORE-BOUNDARY-01 | The repository shall state that ordinary vendor pairs created by the CronJob do not meet the legacy guarded restore metadata/HA identity-capture prerequisites and shall not claim restore compatibility. | README | documentation inspection |
